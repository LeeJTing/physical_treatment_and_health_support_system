# Supabase set-up

Everything the app needs is in this folder. The schema follows the report's
Chapter 4 ERD (Tables 4.81 to 4.108, all 28 entities, every module) and has
been tested against Postgres 16 (`tests/verify_schema.py`, 49 checks).

| File | What it does |
|---|---|
| `migrations/20261006120000_core_schema.sql` | The 28 tables, constraints and indexes |
| `migrations/20261006120100_security.sql` | Row-level security, Data API grants, `account` row at sign-up, `complete_exercise_session` RPC |
| `seed/seed_lookups.sql` | Health conditions, physical limitations, dietary restrictions (Table 3.3) |
| `seed/seed_catalogue.sql` | 16 exercises, 10 treatment plans (generated by `seed/build_seed.py`) |
| `migrations/20261026120000_diet_and_analysis.sql` | M200/M400/M700 additions: `model_version` widened to 60, score band check, `food_item.food_key/plan_role/meal_slots`, restrictions 6–10, private `meal-images` storage bucket with per-account policies |
| `migrations/20261101120000_food_names_and_targets.sql` | "Foods I cannot eat" becomes 36 food names (Onion, Garlic, Pork, Prawn, ...; type `FOOD`, grouped). The labels Vegan, Vegetarian, Halal and Shellfish are no longer offered, and a patient who had one gets the food names it rules out (Halal → Pork, Lard, Alcohol, ...). `food_item` gets saturated fat, fibre, potassium, phosphorus, calcium, caffeine, total sugars, a two-hands flag (arm limitation), a pregnancy caution and the data source |
| `migrations/20261101130000_fail_safe_plans.sql` | A diet plan made under the fail-safe limits (profile unavailable, UC900 E1) is stored without a `safety_limit_id`; the `meal-images` bucket accepts only JPEG/PNG up to 10 MB |
| `seed/seed_food.sql` | The 36 food names and 209 Malaysian and healthcare foods (food-catalogue-2.0: nutrients per 100 g from USDA FoodData Central ingredients and standard recipes, replaced by Malaysian laboratory values for 54 foods) with the 805 food names their recipes contain (generated by `seed/build_food_seed.py` from the AI server's `food_catalogue.json`, so both use the same ids and values) |
| `tests/verify_schema.py` | Runs all of the above on a throwaway local Postgres, in the order below, and checks it |

## 1. Create the project (once, for the whole team)

1. supabase.com → New project. Name `apths`, region **Southeast Asia (Singapore)**, a strong database password (keep it in a password manager, never in Git).
2. In **SQL Editor**, run these files in this order, each as a new query:
   `20261006120000_core_schema.sql` → `20261006120100_security.sql` → `20261009120000_multiple_active_plans.sql`
   → `20261011130000_more_health_conditions.sql` → `seed_lookups.sql` → `seed_catalogue.sql`
   → `20261026120000_diet_and_analysis.sql` → `20261101120000_food_names_and_targets.sql`
   → `20261101130000_fail_safe_plans.sql` → `seed_food.sql`.
   If the earlier ones were run before, run only the ones not run yet, then `seed_food.sql` again
   (it updates the foods and the food names in place).
3. **Table Editor** should show 28 tables in `public`, each marked RLS enabled.

## 2a. Continue with Google (FR100_018 to FR100_023)

The app opens Google's page in the phone's browser through Supabase; Google returns to Supabase,
Supabase returns to the app at `my.edu.tarumt.apths://login-callback` (already in
`AndroidManifest.xml`), and the app signs in. Nothing about Google is in the app build: no client ID,
no SHA-1. Before opening the browser the app asks the project (`/auth/v1/settings`) whether Google is
on, and says "Google sign-in is not available yet" until it is.

1. **Google Cloud Console** (console.cloud.google.com), with the team's Google account:
   1. Create a project, e.g. `HealthGuide FYP`.
   2. APIs & Services → **OAuth consent screen** (Google Auth Platform) → Get started. App name
      `HealthGuide`, support email, audience **External**, contact email. Under **Data access** keep the
      default scopes (`email`, `profile`, `openid`).
   3. **Audience** → while the app is "Testing", add every tester's Gmail under **Test users** (only
      they can sign in), or press **Publish app** (no Google review is needed for these basic scopes).
   4. **Clients** (Credentials) → Create client → type **Web application** (not Android: Supabase,
      not the phone, talks to Google). Under **Authorised redirect URIs** add
      `https://<project-ref>.supabase.co/auth/v1/callback` (Supabase shows this exact address on its
      Google provider page). Create, then copy the **Client ID** and **Client secret**.
2. **Supabase** → Authentication → Sign In / Providers → **Google**: Enable, paste the Client ID and
   the Client secret, Save. The secret stays in Supabase, never in the app or Git.
3. Supabase → Authentication → **URL Configuration** → Redirect URLs: add
   `my.edu.tarumt.apths://login-callback` (without it Supabase sends the browser to the Site URL and the
   app never gets the session).
4. On the phone: Log in → **Continue with Google** → choose the account → the app opens again.
   - First Google sign-in: a new account (`auth_provider = GOOGLE`) and the **Complete Account Setup**
     screen (username and password, FR100_022).
   - The Gmail already has a verified email account: Supabase links Google to it and the app shows
     UC100 M12 (FR100_021). If that email account was never verified, Supabase still signs the
     patient in with Google but removes the unverified email login (to stop account take-over), so
     the old password no longer works; "Forgot password" sets a new one.
   - **Cancel** on the setup screen signs out; deleting the unfinished account (FR100_023) needs
     `supabase/proposed/20261009130000_discard_incomplete_google_account.sql`, still waiting for both
     of us to agree before it moves to `migrations/`.

If it fails: "not available yet" = step 2 not saved; Google's page says *redirect_uri_mismatch* =
step 1.4 address wrong; Google says *access blocked / app not verified* = add the Gmail as a test user
(1.3); the browser stays on a Supabase or localhost page = step 3. `--dart-define=GOOGLE_SIGN_IN=false`
hides the feature on purpose.

## 3. Keys: who gets what

| Value | Where it goes | Secret? |
|---|---|---|
| Project URL | App: `--dart-define=SUPABASE_URL=…` | No |
| Publishable key | App: `--dart-define=SUPABASE_ANON_KEY=…` (named publishableKey in the code) | No, RLS protects the data |
| JWKS URL `https://<ref>.supabase.co/auth/v1/.well-known/jwks.json` | AI server `ai_server/.env`: `SUPABASE_JWKS_URL=…`, `DEV_AUTH_BYPASS=false` | No |
| Secret / service-role key, database password | **Nowhere in the app, the AI server or Git** | Yes |

## Differences from the report (deliberate)

- `account.account_id` **is** the Supabase Auth user id; `password_hash` is not stored because Supabase Auth keeps the password hash itself. The `account` row is created automatically when someone signs up.
- Foreign keys the report writes as `REFERENCES patient_treatment_plan` point at `patient_plan`, the table's name in Table 4.94.
- Extra columns used by the code: `health_profile.version` (FR100_053), `exercise.pose_key`, `treatment_plan.goal`.
- `BALANCE_IMPAIRMENT` is seeded although UC300 C7 does not list it, because Table 4.86 and the risk rule set use balance limitations.
- Dietary restrictions: Table 4.88 only gives examples (PEANUT, SHELLFISH, VEGAN, VEGETARIAN, HALAL). M700 completes the list with FISH, EGG, MILK, GLUTEN and BEEF (10 in all).
- `food_item` keeps the catalogue key (`food_key`), its planner role and meal slots, so the app, the AI server and the database name each food the same way.

## Not covered yet

- **24-hour purge of unverified accounts** (FR100_017): needs a scheduled job (`pg_cron`) or an Edge Function.
- **Profile access log** (UC1000 C4): the ERD has no table for it.
- Free projects **pause after 7 days without activity**; open the dashboard before a demo.
